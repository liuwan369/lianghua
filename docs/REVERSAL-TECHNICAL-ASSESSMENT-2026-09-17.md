## 1. 结论和本次范围

该方案可以实现为独立策略，复用现有系统的市场发现、实时行情、订单执行、账户、订单回报和结算底座。不能把纸面成交器直接改名为真实策略；需要将信号、阶段、真实订单和资金恢复串起来。

本轮目标是停止做市方向，在备份后开发 BTC 五分钟反转策略及普通用户可以操作的页面。用户明确取消新增回测、多日模拟和多日数据观察的前置要求。验证采用快速功能测试及线上现有市场的小额真实订单，不设置“必须再跑 24 小时 paper”或“必须凑第三个日期”之类的时间门槛。

真实订单去重、最高买价、实际成交、资金不能重复使用、重启恢复和结算到账仍是功能正确性要求。它们应通过本地状态和异步回报实现，不应变成每次触发前的多轮串行远程检查。

## 3. 统一后的策略规则

### 3.1 市场和可配置参数

只交易 `btc-updown-5m-{start}` 对应的合法五分钟市场。以 `condition_id`、UP/DOWN 的真实 token ID、开始和结束时间确认身份，不通过标题或赔率位置猜方向。

这是一个 BTC 五分钟反转策略，70 和 75 不是两个策略，也不是必须二选一的固定方案，而是历史运行中出现过的两组参数模板。每个策略实例保存一份可编辑参数版本；保存后的参数只对尚未开始的新场生效，当前场的已创建阶段和订单继续使用创建时的版本。

| 参数组 | 用户可配置内容 | 历史参考模板（不是硬编码） |
| --- | --- | --- |
| 触发与确认 | UP/DOWN 卖一跨价触发阈值、反转确认阈值、最高买价 | 历史记录曾使用 0.67/0.70 和 0.70/0.75 的组合 |
| 阶段 | 每阶段新增份额、最大阶段数、是否允许未成交余量继续工作 | 历史记录曾使用 `5/18/54/130` 或 `5/22/75/236` |
| 资金 | 单场预算、总预算、工作单预留比例、日内停止条件 | 历史金额只用于复算，不构成当前额度或上线门槛 |
| 运行 | 生效场次、运行时长、异常暂停和恢复策略 | 由页面设置，不能写死为某一历史时长 |

参数校验必须使用当前市场的最小份额、价格精度、余额和费用配置；不符合交易所约束时明确提示并阻止该次提交。预算、阶段数和份额可以由用户调整，系统不得暗中替换成历史模板或把历史资金测算当成授权额度。

### 3.2 触发、阶段和确认分别记录

1. 第一阶段允许任一方向产生有效跨价。后续阶段必须是与上一个已创建阶段相反方向的有效跨价。
2. 同方向在门槛附近反复跨越，不消耗新阶段。这采用 `06` 第 3 节的明确限制，消除 `09` 泛称“每次跨价”带来的歧义。
3. 反转确认只在另一方向达到确认阈值时增加计数。首次确认记为 0 次，重复同方向不增加。
4. 跨价创建阶段不等待确认阈值，也不等待上一单全部成交。使用独立的 `last_stage_direction` 和 `last_confirmed_direction`，不能用一个字段混算。
5. 阶段请求份额在创建后固定。订单剩余量由真实累计成交计算，反转不把旧单剩余量变成下一阶段。
6. 市场未结束时继续处理触发和订单回报，不增加“最后 20 秒禁止下单”规则。实际市场已截止或交易所拒绝过期单时不能继续提交。
7. 达到用户配置的阶段上限后仍继续跟踪行情、确认次数、订单及结算，不再创建新阶段。

采用原文01及用户日志的首样本规则：从新场起点开始跟踪、尚无阶段时，首份有效成对盘口的某方向卖一处于`[触发价,最高价]`可创建首单，独立记录`initial_band_entry`，不伪造历史跨价。双边冲突等待。中途首次启动且无状态时从下一场开始；服务重启恢复已有阶段，行情重连只重建跨价参考，均不重做首样本首单。

### 3.3 挂单和真实成交

订单是有最高价格的买入限价单，允许立即吃到当前卖盘，剩余部分继续作为工作单存在。不能强制 `post-only`，不能默认改成只允许一次立即成交后取消剩余的订单类型。

本次官方核验显示 GTD 设定的 expiration 必须至少在当前时间 3 分钟之后，且实际会提前 1 分钟失效，最短有效存续约 2 分钟。因此不能对所有尾盘订单机械设置“本场结束时 GTD 到期”。首版采用可保留余单的 GTC，加场次截止处理及明确撤单确认；不能为绕开 GTD 限制而新增“最后两分钟不交易”的策略规则。

反转不撤旧方向工作单，不自动追到 71/76 美分。未成交旧单和新方向订单可以并存。场次结束后处理剩余订单的到期或撤销，并继续接收迟到成交。

必须纠正桌面方案的价格改善表述：首次提交时，若现有卖盘低于用户设置的最高买价，可能以更低价格成交；但已经按某一工作价（历史示例为 0.70）挂在交易所的买单，后来被卖家打入时通常按其工作单价格撮合，不能拿之后看见的更低卖一回写成自己的成交价。具体撮合和费用口径以当时官方接口及真实回报为准。系统只按自己的真实成交记录计算价格、数量、费用和持仓。

### 3.4 行情有效性

沿用输入规格的新鲜度目标：单边报价最大 2 秒，双边源时间差最大 1.5 秒。实现时必须明确交易所源时间、接收时间、最后快照时间和连接健康，不能把“价格没有变化”直接认作连接已经过期。

失去可信双边盘口时只暂停新触发，保留已有有效限价单。重新连接后先拿当前完整盘口再接增量，不用丢失期间的价格跳变补造多个阶段。两边同时跨价或同时满足冲突确认时不靠数组顺序随机选边，应标记为待确认并等待可判定的新鲜数据。

## 4. 最小状态和持久化

### 4.1 场次状态

`准备 -> 运行 -> 截止处理中 -> 等官方结果 -> 等赎回到账 -> 完成`。

行情异常是可恢复暂停标志，不抹掉当前场、旧单和已成交持仓。新场的触发状态重置，旧场待结算记录继续存在；资金跨场共享，不能每五分钟重置为初始本金。

### 4.2 订单状态

`已创建 -> 提交中 -> 工作中 / 部分成交 / 全部成交`。

附加分支包括 `结果待确认`、`已拒绝`、`撤单中`、`已撤销`、`剩余到期`。发送撤单请求不等于撤单已成功；订单终态不得阻止迟到真实成交补记。

稳定业务键采用 `strategy_instance + condition_id + stage`，方向、参数版本和数量持久化。签名请求发出前保存意图及可追踪的订单身份。网络重试不能创造一个新的经济订单；只有确认原单不存在或明确终结后，才考虑重试或补足实际缺口。

不能假定 Polymarket 接受任意 `client_order_id` 并支持按该字段查询。执行适配层需要确认当前 SDK 的签名订单 hash、返回 order ID 和查单能力，建立本地业务键到交易所身份的映射。

### 4.3 必需保存的数据

保存策略实例及参数版本、市场身份、上次有效跨价样本、阶段方向和确认方向、阶段列表、订单请求与交易所 ID、去重后的成交明细、两边持仓和成本、工作单资金预留、官方结果、赎回状态及到账信息。成交重复推送和重启恢复不能重复增加持仓或扣钱。

参数变更只应用到尚未开始的新场。已创建阶段及其订单不能因为页面修改份额而重新生成。

## 5. 资金、费用和用户预算

### 5.1 统一现金口径

使用一套现金账本：

```text
现金余额 = 期初已确认现金 + 实际充值 - 实际转出
         - 实际买入支出 - 以现金支付的费用
         + 实际卖出收入 + 已确认到账的赎回收入

可用于新单的资金 = 现金余额 - 尚未消耗的有效工作单预留
                 - 已发送但结果未明的请求预留
```

如果交易所接口返回的已经是扣除订单冻结后的可用余额，不能再扣同一笔冻结；适配层必须标注返回的是总现金还是可用现金。原 `04` 的公式不能再额外加“净利润”。

手续费可能体现在现金扣款、收到的份额或其他官方字段中，必须核实并按实际资产记账，避免既减少份额又重复扣现金。金额、价格和份额使用定点数或十进制定量处理。

官方结算可确认应得返还，但未赎回到账的金额不算可用现金。盈亏统计与可用余额分开：净结果等于实际赢家返还减真实成交成本、费用及应归属的实际支出。不能按“最后确认方向”当赢家，也不能把计划份额当实际持仓。

### 5.2 历史参数模板的资金复算（仅供参考）

以下数字只是对用户历史资料中两组参数模板的复算：每一份都按最高价成交、费用为 `0.07 * p * (1-p)`、四阶段方向交替。它们不是两个策略、不是系统默认值，也不是当前用户的资金授权。实际运行必须使用页面中当前保存的触发价、最高买价、阶段份额、最大阶段数、单场预算和总预算；费用、最低数量和余额以当前市场回报为准。

| 项目 | 70 方案 | 75 方案 |
| --- | ---: | ---: |
| 四阶段总份额 | 207 | 338 |
| 四阶段总成本，含假设费用 | 147.9429 美元 | 257.93625 美元 |
| 第 1+3 阶段方向持仓 | 59 份 | 80 份 |
| 第 2+4 阶段方向持仓 | 148 份 | 258 份 |
| 第 2+4 方向获胜的净结果 | +0.0571 美元 | +0.06375 美元 |
| 第 1+3 方向获胜的净结果 | -88.9429 美元 | -177.93625 美元 |

当前代码的订单预留使用另一种口径：`src/platform/polymarket.ts` 对非 `postOnly` 订单按 `p=0.5` 计算每份最大费用，即按当前固定 0.07 系数预留每份 0.0175 美元。历史两组参数按最高价加该费用预留时约需 148.5225 美元和 259.415 美元；这两个数字只用于核对预留算法，不是当前默认预算、实盘门槛或实际手续费。规划和页面必须按用户当前参数计算预留，并清楚区分估算预留与最终成交费用。

同一文件当前成交记账仍使用固定 0.07 系数估算费用，尚未证明来自真实回报。接入前需核实当时官方费率、扣费资产及实际成交费用，分别保存预留费用和最终费用，并在成交或订单终结时释放多余预留。

“前三次常见情况下盈利、第四阶段接近保本”需要赢家、成交数量和费用满足假设，不是所有盘口路径的保证。部分成交、最后方向未被官方采纳、费用变化都能改变结果。

旧文档中的 `$50` 总投入和 `$30` 单日损失是历史讨论假设，已撤销，不能写成代码常量、测试上限或上线门槛；历史资料中的 `$300` 也只是纸面测算。系统应让用户自行填写单场预算、总预算、日内停止条件和阶段份额，并在每次新增阶段前按当前可用余额、有效工作单预留、未决提交预留和交易所最低有效金额动态判断。预算未填写或不足时只阻止超出预算的新增订单，不阻塞底座开发和其他功能验证。

真实接口验证先使用交易所允许的最低有效数量及用户当前可接受的预算，验证认证、限价下单、ACK、撤单、用户频道、部分成交、重启恢复、费用和账户变化。允许小额实际损失，但不得跳过未知订单、重复下单、资金守恒和结算核对。完成最低金额验证不能被表述为已经按历史模板跑完四阶段，也不能推导长期盈利保证。

日内停止条件是用户可编辑的风险参数，不能保证尚未结算持仓的最终损失绝不越线。启动和新增阶段时页面需要展示当前参数下的资金占用、工作单预留和两种赢家结果下的潜在结果，用户确认后由系统按该实例的保存版本执行。

| `src/live/feeds/user.ts` 的 `parseUserMessage`、`parseAuthenticatedTrade` | 解析 MATCHED/CONFIRMED 或 MATCHED/MINED/CONFIRMED 成交状态，但没有 FAILED 状态回退事件 | 按真实 trade ID 持久化成交状态；区分撮合中、链上处理中、确认、失败；MATCHED 后 FAILED 必须可冲正暂记持仓、成本和资金预留，再核对订单真实剩余量，不能重复扣减或直接按原量重下 |
| `src/platform/polymarket.ts` 的 gateway ready 检查 | 使用 `options.markets.every(...)` 要求所有注册市场的盘口及用户状态健康 | 新单检查限定为订单目标市场；换场后旧场行情过期不能拦住新场，但旧场订单和结算仍持续管理 |
| `src/platform/polymarket.ts` 的 `reconcileAfterReconnect` | 交易所 openRows 按当前市场取得，本地 missing 检查却遍历全账户订单 | 对本地订单先按当前 `market.instruments` 的 token 集合过滤，禁止因当前市场查询不含旧场订单就误判旧场订单丢失或终结 |
| `src/platform/settlement.ts` 的 `redemptionPlan`、`settlementAdapter`；`src/cli/platform.ts` 的 connect 调用 | 已有赎回编码和由调用方传入的发送能力接口，但 CLI connect 当前不传 `settle`，没有在该启动路径接通真实 sender | 复用账户签名或 relayer 能力接入真实提交、交易状态查询、失败重试及到账确认；不能把“能编码 calldata”标为自动赎回已完成 |
| `src/platform/polymarket.ts` 的费用预留及 fill 记账 | 预留按最大参考费用，fill 仍按固定系数估算 | 将估算预留与实际费用分开，核对当前官方费率和实际扣费资产，使用真实费用更新账本 |

对 MATCHED 后失败的处理不能只删除一条成交显示。它会影响后续阶段是否有钱、最终 UP/DOWN 持仓和结算结果；必须使资金及持仓变化可追踪且幂等，同时以官方最新状态处理乱序消息，不能让迟到旧消息推翻已确认结果。

### 6.2 下单路径和延迟

热路径采用 `行情事件 -> 本地信号/阶段检查 -> 本地资金预留 -> 签名提交`。市场元信息和费率预取；订单事件持续更新账本；全量账户核对异步运行。发生实质差异或重启时先恢复，再继续新增。不要把每笔新增前“远程查余额、查持仓、查成交、查订单”串起来。

延迟分开记录行情源到接收、接收到触发、触发到提交、签名耗时、HTTP ACK、用户频道事件到达；不把等待市场出现对手方的成交等待时间称为代码延迟。不同机器时钟下的源时间差需注明时钟误差。

官方订单生命周期页说明：部分 crypto/finance up/down 市场启用 **250 毫秒 taker delay**。通过 `GET https://clob.polymarket.com/clob-markets/{condition_id}` 的 `itode: true` 判断具体市场。该等待期间订单不能撤销，API 等待延迟结束后返回最终结果。因此真实 ACK 时间可能包含平台固定等待，不能全算成本地代码耗时，也不能承诺所有吃单毫秒级确认。提前读取并展示该市场属性，订单处于等待窗口时应显示“交易所处理中”，不得超时后盲目重下。

## 7. 普通用户页面所需内容

删除做市专属的双边报价、库存偏斜、补库存、奖励优化等参数入口和描述，保留能被反转策略使用的行情、订单、账户和延迟能力。

- 总览：可用资金、当前运行状态、今日实际收益、待到账金额和需要处理的异常。
- 自动交易：当前五分钟场次及倒计时、UP/DOWN价格、当前参数版本、阶段进度、确认反转数、真实持仓、两种赢家下预计结果和分页订单。
- 策略：顶部选择“BTC 五分钟反转”，进入后按设置页风格分“策略参数”和“运行设置”；参数包括触发/确认/最高买价、各阶段份额、最大阶段数、单场/总预算、日内停止条件和运行时长。不把所有内容铺成一整页，不暴露 JSON 编辑器，也不把 70/75 显示为必须二选一的策略。
- 订单分页：状态筛选、每页数量、上一页/下一页、总记录数；市场显示可识别的场次和方向，长 token/hash 仅作详情。
- 收益：实际成本、费用、官方结果、应得返还、到账状态；未结算不能伪装成已兑现利润。
- 设置：账户接入和系统诊断。启动、停止、保存参数须返回真实结果，页面不能只是会话草稿。

停止新增交易和撤销全部工作单应是不同命令，避免用户查看或暂停策略时误以为旧单已经撤销。运行原因用“等待下一次跨价”“达到四笔上限”“余额不足”“行情恢复中”“等待到账”等直接中文表达。

## 8. 短时功能验证和真实验证

不新建回测项目，不增加多日 paper 等待。快速自动化测试用于规则和故障恢复，小额线上测试用于真实接口行为，两者都不替代为虚构成交。

### 8.1 快速功能测试

覆盖以下可确定行为：

- 0.66 到 0.67 只触发一次；持续在门槛上及同方向重新跨价不新增阶段。
- 新场首份成对盘口在触发价与最高价之间可入首单，超限/双边歧义不入；重启和断流恢复不重复该首单。
- 对侧有效跨价产生下一阶段，即使旧单尚未成交；最多达到用户配置的阶段数。
- 0.66 到 0.71 仍产生最高 0.70 的有效限价意图，不能误标拒单或追价。
- 部分成交、重复成交消息、迟到成交分别正确累计，不重复扣钱或创建整笔补单。
- MATCHED 后进入 FAILED 可正确冲正暂记状态；重复失败、乱序旧消息不能多退资金或抹掉已确认成交。
- 提交超时和服务重启能够恢复原订单身份，不能重新下第一阶段。
- 行情断线/双边冲突暂停新触发，恢复不回放虚构阶段。
- 换场不串 token 和参数版本；旧场结算未到账时资金仍不能重新使用。
- 新场订单不受旧场过期盘口阻塞；按当前场重新对账不误删其他 token 的真实订单。
- 官方赢家与最后确认方向不同时按官方结算；费用不重复扣、返还不重复加。
- 单策略实例锁、分页筛选、参数保存和刷新恢复正常；参数修改只在新场生效，当前场订单继续按原参数版本管理。

### 8.2 小额真实接口验证

按用户当前填写的预算，先确认市场当前最低数量和费用，再使用交易所允许的最低有效金额完成必要的真实订单。预算不是历史 `$50/$30` 常量；每一步使用真实订单 ID 和交易所回报记录结果：

1. 认证账户和当前市场数据可读，实际余额、持仓和订单身份可以对应。
2. 真实限价提交返回 ACK，订单可查询，并在用户频道出现相应事件。
3. 真实工作单撤销可确认；已成交部分保留，取消请求之后的回报不丢失。
4. 至少一笔实际买入成交，价格、份额、费用和账户持仓一致。
5. 进程恢复后找回本系统工作单及场次，不重复提交。
6. 五分钟换场正确，旧场按官方结果计算，具备赢家持仓时完成赎回及到账链路。

部分成交、超时等罕见路径先由执行层自动化测试覆盖，不必等线上偶发数天；线上未实际出现的路径必须如实标注。真实验证尚未出现赢家持仓或到账回执时，不能把赎回标为已通过。官方处理尚未结束就显示“待结算/待到账”，不阻塞其他开发工作。

小额接口验证是系统技术验证，不等于已经按原始 147.94/257.94 美元资金需求跑完四阶段，也不等于长期盈利保证。

## 9. 开发完成的判断

当天开发目标应是：已有系统完成备份；反转策略接入公共底座；原做市入口移除；参数与运行状态持久化；页面普通用户可操作；快速测试通过；按用户预算和交易所最低有效金额采集的真实接口证据可查看。当前文件不将这些项目提前标记完成。

策略完整实盘还需要用户为当前参数填写可承受的单场/总预算和日内停止条件，确认当时官方最低数量、费用和结算接口可用，并完成实际订单和恢复链路。这些是明确待办，不是要求等待更多历史数据，也不绑定历史资金数字。

### 10.1 成交状态与身份的具体实现要求

原始用户频道以 `event_type=order/trade` 分类；成交消息的 `id` 为 trade ID，`taker_order_id` 及 `maker_orders[].order_id` 用于关联订单，`trader_side` 区分本账户角色。`fee_rate_bps` 是费率字段，不能直接当成已扣的费用金额；费用最终数额需要结合成交价格、数量、角色和可核对的实际扣款确认。

新统一 TypeScript SDK 示例把状态包装为 `TRADE_STATUS_*`，原始 WebSocket 和 Python 示例使用 `MATCHED` 等状态。适配层要按实际使用接口规范化，而不是把包装字段直接塞进现有原始消息解析器。

已接收 MATCHED 后，必须继续接收 MINED、RETRYING、CONFIRMED、FAILED 及可出现的 MATCHED_NOT_BROADCASTED 更新。可以先将匹配量计为待确认风险敞口，使下一阶段及时决策；只有成功确认后才能视为最终链上成交。失败时冲正对应暂记变化，再获取订单实际状态，不能凭 FAILED 自动下相同份额的另一张单。

此次 5 页核验确认支持“先签名后提交”和返回交易所订单 ID；没有验证当前 SDK 的本地 hash 方法及其与交易所 order ID 的一致性。因此下单结果未明的恢复实现，需要用当前 SDK/交易所的真实身份匹配做功能验证。不能把“有一个本地客户端编号”当成天然拥有官方幂等查询能力。

### 10.2 当前 SDK 与资金资产的兼容核对

官方示例目前使用 `@polymarket/client` / Python `polymarket` 统一客户端。这不构成整库 SDK 迁移要求。保留现有 SDK 和适配层，优先核对真实必需能力：当前订单签名域与字段、钱包 signature type、订单身份和查询、市场最小数量/tick、实时消息状态、adapter 地址、实际抵押资产、费用字段及赎回发送路径。只有确有不兼容时，替换最小相关调用。

官方生命周期及持仓页使用 **pUSD** 作为交易和赎回抵押物，费用页使用 **USDC** 表达费用计价。页面显示的美元金额不能代替链上资产身份；实现必须记录 token 地址、精度及实际收付资产，不能因为同为美元单位就把 USDC、USDC.e、pUSD 余额相加当成可直接下单资金。

本次官方核验加强了原评估的实施要求，没有引入回测或多日等待门槛。新增的具体开发点是目标市场 `itode` 展示、GTD 时限兼容、完整成交状态恢复、当前 SDK 身份匹配以及 pUSD 赎回实接；这些都可以通过代码修正和短时真实接口验证完成。
