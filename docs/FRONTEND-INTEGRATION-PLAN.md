# 新控制台接入与模块化验收方案

日期：2026-09-09。状态：设计基线已保存；接入第一批已在本地完成并通过回归，以下仍不是实盘验收报告。

## 1. 保存范围与交付目标

用户确认暂定六个页面：总览、自动交易、市场、订单、收益、设置。保留当前布局与风格，接入现有系统，逐项验收后替换旧页面；日后按业务模块修改。

设计回滚点：Git 提交 `269f8ab`，标签 `ui-demo-2026-09-09`。包含 `demo-trading-console.html`、`demo-settings.js/css`、`demo-rewards.js/css`，均位于 `docs/`。相关说明见 [设置演示](DEMO-SETTINGS-2026-09-09.md)、[收益规则](REWARDS-RULES-2026-09-09.md)。不复制多套项目目录。

用户认可的是设计。演示页里的盘口、状态、按钮不等于正式能力；原始内联示例动作与后加载覆盖脚本不能直接带入正式版。正式页面须从真实接口渲染，未知值显示 `--`，无数据、断线和未实现分别说明，不伪造正常、成交或收益。

## 2. 代码核对结论

本次依据本地源码核对，未重新连接服务器确认运行状态。

| 已有组件 | 已有能力 | 接新页面的缺口 |
| --- | --- | --- |
| `_external/btc-5m-market-trading-bot/src/live/` | engine、orchestrator、executor、orderbook、feeds、account、journal 等模块 | 保留交易路径，补参数映射、统一事件和状态输出 |
| `scripts/system-dashboard-server.py` | 静态页、行情、账户、交易启停、日志统计 | 路由/进程管理/统计混在一起；拆成可单独测试模块 |
| `scripts/dashboard_account.py` | 账户检查与安全保存 | 新页面接入已有接口；不重做第二份账户逻辑 |
| 日志汇总 | 单次运行成交额、费用、市场结果、有限条数的最近事件 | 不是跨运行订单账本；缺完整分页、账户隔离、奖励对账 |
| `docs/demo-*` | 六页设计及部分演示交互 | 没有正式接口接入，不可直接作为生产前端发布 |

现有 API：`GET /api/live`、`GET /api/trading/status`、`GET /api/trading/log`、`POST /api/trading/start`、`POST /api/trading/stop`、`GET /api/account/status`、`POST /api/account/check`、`POST /api/account/save`。

未发现独立配置版本、完整订单历史、奖励账本或全链路延迟 API。状态接口当前带日志/进程等技术字段；新前端使用专门的用户数据结构，不直接铺开原始输出。

补充源码核验：`live/engine.ts` 使用 `targetClone()`；页面传入的成本值没有同步覆盖 `hedgePairCostCeiling`，`strategy.ts` 的强制补仓路径还可能将基准上限放宽最多 0.01（封顶 0.999）。因此目前不能承诺用户填写 0.99 后所有补仓都受同一硬上限约束。接入前要统一全部开仓/加仓/强制补仓/吃单路径的优先级，且修正与实际入口不一致的配置注释。

## 3. 模块方案

采用模块化单体：前端 TypeScript + Vite，保留当前 HTML/CSS 风格并拆成六个页面模块；接口服务继续 Python，交易引擎继续 TypeScript。当前阶段不迁移 Rust、不拆微服务、不为每个页面启动一个后端。收益账本和网络请求不得阻塞盘口处理与下单热路径。

建议目录是实施目标，当前尚未创建：

```text
web/src/
  app.ts                  路由、模式、账户与运行上下文
  pages/                  home / trade / markets / orders / earnings / settings
  components/             余额卡片、订单表格、参数输入、错误与空状态
  api/                    请求、认证过期、超时、订阅重连
  state/                  共用快照，禁止各页面自行计算不同的盈亏
scripts/dashboard/        API 路由、账户适配、配置、启停、市场、账本、奖励、监控
contracts/                API 字段、事件及配置的版本化定义与示例
tests/acceptance/          按功能编号组织的接口与浏览器验收
```

| 后端模块 | 唯一职责 | 页面消费者 |
| --- | --- | --- |
| account | 身份、余额、授权、连接检查、安全凭据保存 | 设置、总览、启动预检 |
| config | 参数校验、保存版本、运行实际生效版本 | 设置、自动交易、总览 |
| control | 启停、运行状态机、进程恢复、重复命令处理 | 总览、自动交易 |
| market | 市场元信息、盘口、数据新鲜度 | 市场、自动交易、总览 |
| ledger | 委托生命周期、成交、库存、结算、费用 | 订单、收益、自动交易、总览 |
| rewards | 官方规则版本、账户资格、估算、已确认/已到账奖励 | 收益、总览 |
| telemetry | 八个延迟点、连接状态、样本与更新时间 | 设置、总览 |

采集日库保留。新增独立 SQLite 业务账本，保存运行、配置版本和去重事件；后台增量投影，避免每次网页刷新重扫全部日志。引擎与接口服务先通过本机结构化事件/快照适配，暂保留旧接口兼容层。事件序号断档必须补齐或标记不完整，不可悄悄丢弃；业务账本不是原始行情日库的替代品。

## 4. 参数接线清单

正式配置以服务器为准。浏览器只保留非敏感草稿，不以 localStorage 作为运行配置。显示“已保存版本”和“本次生效版本”，启动绑定版本；运行中保存默认下次启动生效。下一场生效属于后续能力，未实现不得可选。

| 页面字段 | 现有接线 | 待完成与验收 |
| --- | --- | --- |
| 每单金额 | `order_usd` | 以市场 tick、最小份数、费用和余额检查；不得擅自加大金额 |
| 配对硬上限 | `pair_cost_max` | 当前引擎将同一值赋给两个成本配置；拆出目标与硬上限，逐笔证明实际使用 |
| 目标成本 | 未单独暴露 | 与硬上限分别校验；奖励不可降低成本；显示配对量与未配对库存 |
| 策略总资金、单场资金 | 没有对应独立页面 API | 区分现金、冻结资金、持仓占用；未结算资金不得重复花费 |
| 累计提交上限 | `max_total_usd` | 是累计提交金额保险丝，不是单场预算或成交额 |
| 单边未配对上限 | 未独立暴露 | 多挂单同时成交仍不能绕过风险预留；自动值不是已证明最优公式 |
| 挂单等待 | `maker_life_sec` | 明确撤单确认前仍占用风险额度；改价不是盲目重复挂单 |
| 补仓等待、停止开仓/停止补仓时间 | 未完整暴露 | 秒数与市场结束时间对应；优先级和临界时刻测试 |
| 双档/档距、吃单补齐/滑点/损失限额、减持 | 有部分内部执行逻辑，不等于配置闭环 | 各自完成风控、费用、部分成交和失败验收才启用 |
| 模式、时长、最大订单数 | `mode`、`duration_min`、`max_orders` | 0 时长的持续运行含义、停止结果、纸面/实盘彻底隔离 |
| 日亏损停止、并发市场数 | 未独立暴露 | 指定日界线及损失口径；跨市场资金和持仓预留测试 |
| 行情过期阈值 | 有 250ms 盘口门槛，另有 `pm.isHealthy(5_000)` 通道健康检查 | 分清盘口年龄与通道健康时间，不视为同一参数；改为受限配置，主/用户通道断开与时钟异常分别处理 |
| 断线处理、停止后持仓、何时生效 | 非完整用户配置能力 | 停新单→尝试撤单→核对；失败显示未撤净；保留持仓不等于平仓 |
| 内部决策间隔、撤单阈值 | `decision_interval_ms`、`defensive_cancel_bps` | 新页未展示时保留明确的版本默认值，不静默改变行为 |

服务端拒绝未知字段与未支持选项；前端和引擎使用同一单位定义。价格、金额、份数采用可审计的定点/十进制精度规则；UI 四舍五入不得改变风控实际值。每个配置字段均需“保存→重开页面→启动→实际生效快照→对应行为”证据，不能只测试表单保存成功。

## 5. 数据与接口约定

- 新契约使用 `/api/v1/`，旧路由在迁移期间适配；同一个公网地址与登录保护。
- 响应携带 schemaVersion、accountId、mode、runId、asOf、数据来源/完整性；配置另带 revision。没有账户数据的公开市场接口可不带 accountId。
- 总览复用收益/订单模块的汇总结果；不重复统计。历史查询按账户、纸面/实盘、时间筛选，使用稳定游标分页。
- 活跃状态先获取快照再订阅 SSE 更新，事件带序号；断线恢复补齐快照。轮询仅作页面状态降级，不替代交易引擎 WS 行情。
- 启停按钮均有处理中、成功、失败反馈。启动幂等、重复点击只有一次运行；停止先拒新单，订单未确认撤销时不能显示“全部撤单成功”。
- 正式页初始化完成前禁用交易按钮，只允许一套事件绑定；任一模块加载失败不能回退到演示脚本的固定成交逻辑。保留同源/HTTPS 校验、控制令牌、显式实盘确认与服务器解锁，不由前端模式按钮绕过。
- 委托 ACK、成交、链上确认和最终结算分开；撤单期间仍可能成交。订单/成交/结算分别按稳定标识去重，乱序回报不得使状态倒退。
- 未获取费用使用未知值，不能默认 0；已知为 0 才显示 0。交易净额是否已含费用必须随字段声明，防止二次扣费。
- 已结算交易毛盈亏 − 尚未包含的实际费用及其他成本 + 已到账奖励 = 已结算净收益。未实现盈亏、未到账奖励、估算奖励单列；转账/充值不算收入。部分结算及未知成本标注完整性。
- 奖励保存来源、活动适用时间、规则版本、资格、估算依据和结算凭据；成交量档位按官方加权量口径，不拿订单提交额套用。官方未提供的字段显示未知，不承诺精确公共排队名次。
- 不同结算资产分开汇总；若展示折合金额，附汇率与时间。推荐/Builder 等非策略收入可计账户收入，但单列，不抬高 BTC 策略成绩。奖励付款使用唯一标识去重。

不以不断延长一天/三天/一月回测作为交付标准。软件验收用确定性故障与边界测试，加一轮完整真实行情纸面闭环；若没有自然成交则明确该环节未验证，以受控测试验证逻辑，不能制造真实成交。收益是否稳定另属策略评价，软件通过不代表盈利保证。

复杂度：接口/账本与配置闭环高，六页接入与视觉保留中，设计冻结低。当前不报无依据的完成时间；每批以验收项清零为结束标准。重点风险是配置名相同含义不同、纸面和真钱串账、重复回报重计、断线误报撤净、奖励比例误套、模块化时扰动下单路径。
