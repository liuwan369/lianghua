# 都柏林 CPU 资源诊断（2026-09-10）

采样日期：2026-09-10。以下为当次只读测量，不能作为实时资源状态。

## 结论

两个问题同时存在：虚拟机获得 CPU 时间明显受限，以及系统有可避免的重复计算。目前不能仅凭高 steal 断定必须升级，也不能承诺优化代码后就完全解决云端 CPU 供给问题。

## 实测

- 实例 t3.small，eu-west-1，2 个逻辑 CPU，约 2 GB 内存。
- 20.25 秒采样：steal 79.03%，idle 0.86%，iowait 0%，load average 2.84 / 3.21 / 3.10。MemAvailable 1,163,124 kB，暂无内存耗尽证据。
- 控制台 CPUQuota=infinity，cgroup 没有 CPU 限流；CPUWeight=1000 仅改变同机竞争权重，不增加云端配给的 CPU。
- 采样时采集器、历史分析器均消耗 CPU；历史分析服务为执行中的 oneshot，从 06:22:36 UTC 开始处理。
- 单次控制台快照的 cProfile 只读剖析：墙钟 1.671 秒、进程 CPU 1.463 秒；178 次 zlib 解压、200 次 JSON 解码。该剖析有测量开销，是一次样本，不是长期基准。

## 软件开销来源

1. `scripts/system-dashboard-server.py` 的后台刷新在每轮结束后等待 1 秒，再启动子进程重算。每轮读取/解压最近 180 秒 CLOB 数据，重建盘口；大多数窗口数据与上一轮重叠。它不依赖浏览器点击。单次剖析的 SQLite execute 总计约 0.005 秒，主要成本在解压、JSON、Python 循环和盘口重建，不能简单归因于数据库查询慢。
2. `pm-r25-dublin-live-analyzer.timer` 每小时触发一次过去 24 小时证据分析。任务重新解压/排序/重建历史盘口，并处理 Binance 等证据流；相邻小时的数据窗口高度重叠。这是研究分析任务，不是实时下单所必需的热路径。前端代码检索未发现消费该报告文件的路径。两天证据库当前约 1.12 GiB 和 0.19 GiB，未做全库扫描来测量。
3. `scripts/dashboard/projection_worker.py` 约每 250 毫秒检查日志、计算摘要并写快照，即使日志没有新记录；有增量摄取和批量上限，但空闲时仍有可优化的轮询/快照写入。其相对占用不应与高成本盘口重放等量看待。
4. 账户检查每次启动 Node 并加载较大的 SDK，存在冷启动开销，编译缓存仅缓解，不替代常驻服务或缩小依赖路径。无模拟负载的账户检查 HTTP 200、耗时 21.47 秒；模拟负载下出现 HTTP 504，仍需解决。

行情采集本身承担真实证据保存，不能把它所有 CPU 使用都视作浪费；优化不能通过丢事件、删功能、降低数据真实性来凑指标。

## 尚未查明的云端原因

高 steal 表示虚拟机等待云平台调度 CPU；可能与突发实例 CPU 积分/配给或宿主调度有关，不能仅用该指标区分。尝试使用实例现有 IAM 角色只读查询 CloudWatch CPUUtilization、CPUCreditBalance、CPUSurplusCreditBalance、CPUSurplusCreditsCharged 均返回 AccessDenied；EC2 credit mode 查询返回 UnauthorizedOperation。因此积分余额和 standard/unlimited 模式未核实，没有修改 IAM 或计费配置。

## 建议的处理顺序

先把控制台盘口改为常驻增量状态，每条新行情处理一次；历史分析与在线服务隔离、改增量统计；账本无变化时避免重算，账户检查减少冷启动。保留全部原设计和数据语义。然后在相同行情负载下复测 CPU、盘口新鲜度、账户检查 p95 和丢包/队列。最后再依据实际剩余需求及 AWS 积分指标，判断是否迁移到稳定 CPU 的实例或增加资源。当前没有证据支持“只升级就解决所有问题”。
