## 0. 本轮决定与执行方式

用户已授权主 Agent 组织系统开发、服务器管理、部署、调试、参数优化和问题修复；旧文档中反复等待用户确认、仅因历史人工锁而停止推进的工作要求不再适用于已授权范围。遇到问题先复现、查官方和外部资料、比较方案、修复并验证，及时修正计划和 Agent 任务，不等待用户逐项指导。

正式主线是奖励经济性下的自动做市。交易本身收支平衡可以接受；交易有受限损耗时，也应研究真实可获得的返佣/奖励能否覆盖全部成本。零奖励结果用于压力测试，不再作为所有候选进入实验的统一否决条件。

三端定义为本地源码、Git 远端、都柏林部署。每批交付都以同一发布版本、配置版本和证据清单核对三端，更新文档并保留回滚路径；未经实际核对不能报告三端同步完成。

前端保留现有页面、布局和配置入口，不重新设计或重写。先测试策略，再提供经过验证的默认参数，减少用户逐项填写和误配；内部自适应参数按策略验证结果逐步接入。只对实际数据、交互或性能缺口做必要补充。修正过程中的错误和假设属于维护本规划，不随意扩展到无关平台或交易品种。

“最高质量”落实为可复现验证、独立审查、可观测运行、自动故障处理和可回滚发布；不承诺软件永远无缺陷或市场收益没有波动。

## 1. 交付目标

在 Polymarket BTC 五分钟 Up/Down 市场持续评估做市机会，通过小批量报价、库存偏斜、受限补轻侧和尾盘退出，争取可持续的账户净收益。收益研究覆盖交易损益、符合条件的返佣及流动性奖励。BTC 信号用于报价和风险判断；严格低成本配对作为对照基线。

最终系统应能自动发现市场、校验行情与资金、报价和撤单、处理成交及异常、管理库存、核对结算和费用、展示完整运行状态，并在无合适机会或风险超限时暂停交易。

交付分成两条独立验收线：

- **系统线**：软件、数据、账户、订单、运维和控制台通过验收，可以在限定条件内自动运行。
- **策略线**：冻结版本在独立样本和小额真实交易中取得可解释的费用后结果，风险与不确定性满足事先约定的门槛。

工程工作可以完成系统交付，但不能承诺未来利润。策略证据不足或为负时，应继续研究或保持停用，不通过增加额度或更换收益口径把它标为通过。

### 已确定的真实资金边界

用户在本轮明确：总投入 50，单日最大亏损 30。按平台美元计价口径记录：

| 项目 | 上限或规则 |
| --- | --- |
| 本金投入 | 50 美元；首次验证不自动补充本金 |
| 交易风险额度 | 不超过 50 美元及实际可用资金，盈利不自动提高上限 |
| 单日损失硬预算 | 30 美元；风险日为北京时间 Asia/Shanghai 自然日 |
| 内部资金分配 | 在 50 美元内按盘口、最低份数、库存、费用和退出需要动态分配 |
| 内部软阈值 | 由运行数据推导；不另外固定 10 美元启用额度或 5 美元日停止线 |

总投入是本金预算，不是累计成交额；资金周转不会自动获得追加本金许可。美元计价不代表可以把不同抵押资产余额直接相加，实施时须核对实际资产和计价口径。

日损失按当日初始权益、剔除充值提款后的当前权益计算，同时包含未平仓风险；不只统计已平仓交易。未结持仓、在途订单、未知成交与费用预留需保守纳入下单前预算。停止线和风险状态跨重启持久化，跨日不清除未核对敞口。风险日报与 UTC 研究切分分别标注时区。

30 美元为用户设定的外部损失上限；软阈值、单笔和单场份数按证据动态调整，避免设置没有依据的额外固定限制。下单前预留费用和退出风险，异常成交或滑点仍可能越线，不能把触线后撤单当作损失保证。当前本轮修改的是规划，未因此启动真钱交易。

## 3. 先后顺序

```text
P0 基线与验收规则
  -> P1 数据可信 + 交易基础可靠（并行）
  -> P2 回放可比较、可复现
  -> P3 做市策略研究与独立验证
  -> P4 冻结候选的 shadow / paper 连续运行
  -> P5 限额真实执行校准与财务核对
  -> P6 自动运行交付与受控扩容
```

数据采集贯穿各阶段。控制台缺口按交易流程逐步补齐；第一阶段只建设必要的工程工具，使主要投入尽快转向策略。

### P0：固定基线和判断标准

工作：记录源码 SHA、现有修改、配置来源、运行环境与历史证据；复现现有测试/构建；建立统一验证入口、可重建依赖和基础 CI；冻结本批任务范围。

同时确定实验口径：资金规模、手续费、奖励分类、参数搜索次数、数据切分、主指标和失败条件。真实资金遵守已确认的 50 美元本金和 30 美元单日损失外部上限；默认先用离线、mock、shadow 或 paper 验证。只有真实执行才能补齐的证据，可在相关资金、订单及恢复路径已验证后提前插入有界实盘探针，不必机械等待全部研究完成。

优先核对 50 美元本金能否同时满足市场最小份数、双边资金占用、奖励最低挂单量和退出预留。参考账户的约 30 份批量不是本账户的默认下单量。先通过调整层数、份数、报价和资金复用寻找可行方案；某类奖励确实不适用时单列原因，继续验证其他收入路径，不因一个资格条件不符终止全部研究。

产物：基线报告、任务清单、统一验证命令、初版验收矩阵。

通过条件：现有失败已修复或明确隔离为有负责人、可复现的阻塞项；交易关键路径失败不能豁免。所有后续结果绑定源码与配置版本。

### P1：数据和执行基础并行完成

数据工作：校验同市场双边 token、tick、最小份数、事件时间和接收时间；补官方 resolution/outcome；记录当期费用及奖励资格、配置起止时间；标注缺失、乱序、重连和覆盖率。

执行工作：复现并修复资金预留、待确认/待撤占用、日损失与停机状态跨重启恢复、未知订单和迟到成交处理；核对唯一生产入口、账户切换、启动和退出行为。完善行情过期、队列积压、磁盘和 CPU 影响的观测。

产物：带哈希的数据清单、结算覆盖报告、故障用例、持久化风险与资金状态、运行指标。

通过条件：缺失关键输入不能变成可交易默认值；未核对订单不能释放资金；重启不能重置已触发的风险限制。缺官方结算的市场只能出情景分析，不能计入已实现结算收益。

### P2：校验回放器

回放盘点与适配可以在 P1 修复期间并行进行；P2 最终验收和基线冻结必须等待 P1 的执行语义冻结、相关修复集成，并对集成版本重新完成差分验证。

工作：明确 TypeScript 生产策略、Python shadow 及旧 backtest CLI 的差异；生产候选使用同一策略逻辑，或用同事件输入的差分测试证明决策、份数和风险口径一致。Python 研究引擎不能未经对照直接代表生产结果。

回放应覆盖排队假设、部分成交、在途订单、撤单未确认、手续费、尾盘退出和跨市场资金预算。成交模型给出保守/中性/压力情景；未测参数标明假设。

使用 collector 接收时间回放时，不重复叠加已经包含的公开行情传输延迟。订单 ACK、挂单可见和成交是不同事件；零成交策略不参与盈利排名。

产物：回放验证报告、策略一致性样本、执行假设清单、固定数据与种子的可复现命令。

通过条件：每个参数能证明实际生效；相同输入结果可复现；订单和库存守恒；官方结算收益与最坏结算情景分开；留出市场完整且有足够有效活动。小规模烟雾测试只用于证明流程可运行。

### P3：主攻做市策略

持续研究参考地址 `0x3048d65321be3497164cdfc2996f94f98a2e7537`，结合官方 SDK、公开机器人和微观结构研究形成假设；每个借鉴都记录来源、版本、适用条件、移植位置及对照实验。实施流程见第 7 节。

按顺序做有界实验，每次先控制一个机制，再验证组合：

1. 重建 strict pair 和当前 v2 的基线，解释亏损、缺边与不参与的原因。
2. 优化小批量报价、挂单层数、库存 skew 和补轻侧，观察参与率与资金效率。
3. 加入盘口深度 microprice、短时波动、订单流和成交后 markout，过滤不利成交。
4. 校准成交/队列概率，研究最短挂单寿命、重报价阈值和丢失队列的代价。
5. 优化尾盘阶段、分层退出和最小份数残余；60/30/10 秒是现有候选规则，需要比较验证。
6. 接入奖励资格和净经济性：只有适用的市场/账户/时期才估算，奖励下降时主动缩量或停止。

使用按时间前推的训练/验证/最终留出集。相关样本按日/市场组处理，跨边界特征和标签做清理或留间隔；同一市场不能分散到训练和测试。训练与验证可以选择参数；最终留出结果一旦用于调整，就需要新的未看过的数据再评估。

记录所有尝试，按信息增益安排有界搜索，报告相对基线的变化和失败方案。先粗筛再局部精调，缓存不变输入并复用同一数据版本；低价值组合提前结束但记录停止规则和中间风险。使用可解释统计与轻量模型建立基线，复杂模型以增量效果和运行成本决定是否采用。

产物：策略对照表、参数版本、成本归因、概率校准、日级收益/回撤、尾部损失及未配对风险报告。

通过条件：有效成交和日期覆盖达到预注册要求；独立样本结果及不确定性支持继续验证；风险不突破预算；优势不依赖乐观成交或未经证实的奖励。

### P4：连续 shadow / paper

冻结候选代码和自适应规则版本，接真实行情，验证跨市场切换、重连、限流、慢账户查询、资源竞争、停止和重启。规则内的动态参数可以变化，每次变化须记录输入、原因、范围与版本。核对报价到成交的状态变化、参数运行快照和账本一致性，按第 8 节完善六页控制台。

先验证故障恢复、足够的市场切换和有代表性的负载，再随数据累积延长观察。72 小时/7 天可以作为报告窗口，不设为所有修复的机械等待期。影子运行不证明本人真实排队、实际奖励或实盘盈利。

通过条件：无未解释订单/账本差异；关键恢复用例通过；数据新鲜度、延迟与资源指标满足事先冻结的标准；策略行为符合回放预期，差异有可复核解释。

### P5：小额真实执行校准

候选持续实盘的前提是相关数据、订单、资金和故障路径通过验证，账户与执行参数可追踪；遵守用户已确认的总投入 50 美元、单日最大亏损 30 美元。主 Agent 自行制定范围内的单笔、单场和退出配置，完成发布、启停与核对，不重复索要已有授权。历史人工锁按当前任务需要更新，防重复下单、资金守恒及有效凭据校验继续作为正确性要求。

分两部分：先用有限探针确认 ACK、成交、撤单、余额、结算和回执，再运行冻结候选的小额试验。记录真实排队/成交偏差、逆向选择、费用和到账奖励。部分成交等自然场景尚未出现时标注缺口，以故障注入补充工程验证，不能伪称实盘已覆盖。

建立期初资金、充值提款、在途资金、持仓及期末资金的统一账本。完成奖励付款周期或仍有未结项目时分别标注，不提前确认收益。

通过条件：实际风险受限，账户全流程可核对；真实执行成本没有推翻策略优势；收益和风险样本达到事先约定要求。结果不通过时回到相应研究阶段，保留停止和风险状态。

### P6：自动运行交付

交付自动启动/恢复、行情与账户健康检查、报价和风控、对账、监控告警、备份恢复、发布校验和回滚。暂停必须保持跨重启有效；恢复交易需满足状态核对与既定政策。

研究任务与在线交易隔离资源。候选模型自动生成报告；生产代码及自适应规则版本固定，规则内参数按第 8 节动态变化。新规则由 Agent 完成对照评估、审查、发布和回滚准备后晋级，避免一次偶然高收益导致版本替换。

持续覆盖完整奖励结算周期和不同市场状态，并给出 14/30 天等滚动报告；由有效样本、风险和执行质量决定验证深度，不以固定天数延误已经可验证的功能修复。在已授权资金内自动调整占用，检查成交质量、容量和回撤；50 美元本金和 30 美元日损失仍是用户的硬条件。

产物：可运行版本、六页控制台、部署/回滚/恢复流程、自动研究与监控任务、完整验收报告和策略证据报告。

## 4. 如何判断盈利

统一账本先列已结算交易损益，再扣除尚未计入的实际成本，加入已确认到账的返佣/奖励。充值提款不是利润；手续费、退出亏损和 markout 不能重复扣减。markout 用于诊断，实际退出损益通常已经包含在交易损益中。未结持仓单列估值及风险，不当作已实现收益。

三种口径必须同时输出：

| 口径 | 用途 | 能否作为盈利证据 |
| --- | --- | --- |
| 零奖励 | 衡量裸交易损耗、补贴依赖和停发压力 | 单独判断交易本身经济性 |
| 官方规则估算奖励 | 判断机会、资格和保守收益区间 | 只用于研究，不能确认为到账利润 |
| 实际归属并到账奖励 | 结合完整钱包账本评估总经济性 | 可以，但需覆盖归属周期和全部成本 |

零奖励压力测试要求损失受预算约束；本规划不要求每场最坏情景都不亏。若策略主要靠奖励覆盖损耗，应有真实账户证据、规则变化监测和奖励停止时的退出预算，否则仍为未验证。

预注册收益评估包括：奖励后的平均净收益、裸交易损耗、按日分组的不确定性区间、最大回撤、尾部损失、单边暴露、资金效率、有效市场覆盖和成本压力。按日或相关市场组估计置信区间；95% 下界大于零可以提供较强盈利证据，但不作为所有工程修复、模拟或有限实盘校准的统一开关。具体方法、样本停止规则和主指标在查看留出结果前记录。

样本不足、置信区间过宽、只在少数日期盈利或只剩估算奖励时，标为 INSUFFICIENT_EVIDENCE，同时安排能降低不确定性的下一项实验。交易收支平衡而真实奖励带来净收益是可接受结果；预计奖励必须有当前规则、资格与保守分配依据。未知奖励不填造，单一软指标不符也不自动终止整个策略方向。

最终分别报告 SYSTEM_READY、STRATEGY_VALIDATED_WITHIN_TESTED_SCOPE 或对应未通过状态；验证结论始终附适用版本、资金规模、时期和成本条件。

## 10. 三端同步、回滚和文档更新

每批发布步骤：记录本地与线上现状 -> 冻结本批 diff -> 验证与审查 -> 提交/推送 Git -> 构建与生成发布清单 -> 备份线上将替换的文件/配置 -> 部署 -> 核对源码、构建哈希、配置、schema、服务和 API -> 更新当前文档。只有全部核对后标为同步完成。

发布清单记录 release_id、Git SHA、构建文件 SHA256、配置版本、schema 版本、时间、验证报告、部署目标和回滚目标。源码与构建产物用途不同，线上无需保存依赖目录到 Git；秘密和原始数据库不进入远端代码库。同步目标是可证明版本一致，不是无差别镜像覆盖文件夹。

版本回滚由 Agent 自行执行：先停止新增订单并核对开放委托/持仓，再恢复兼容的代码与配置；保留新产生的成交、账本和风险停机状态，数据库变更要求兼容或显式迁移路径。回滚不撤销链上交易，也不能清空日损失。版本恢复后重做健康与三端核对。

所有活跃说明随功能更新：删除或改写已失效的当前描述、旧授权等待语句和重复入口；确认无引用且无证据价值的旧文档删除。历史测试、真实交易和研究证据归档并标日期/版本，不篡改成当前结果。索引只引导到最新入口，历史链接有明确状态。

发现问题时主 Agent 将其映射到现有阶段，更新目标假设、负责人、依赖、验收和修订记录；Agent 按最新任务卡纠正，不擅自偏离自动做市主线。计划、实现、部署、验证分别记状态，保持一个当前事实来源。
