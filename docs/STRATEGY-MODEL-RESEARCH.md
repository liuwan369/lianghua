# 动态补仓模型研究

更新时间：2026-09-05

## 结论

当前系统已经有数学风控，但还不是“最优补仓器”。它能计算平均配对成本、预计补仓后的成本、两边数量差和最坏亏损；不过生产配置仍以固定份数 `clipShares` 为主，成交概率、排队位置、盘口深度和奖励没有全部进入同一个优化公式。

正确方向是：每次盘口或成交变化，都重新计算“买哪一边、买多少、挂什么价、等多久”。收益排序只能放在硬风控之后。

## 已核对的公开实现

### 1. 本项目 TypeScript 引擎

文件：`_external/btc-5m-market-trading-bot/src/strategy.ts`、`inventory.ts`、`risk.ts`

已有能力：

- 用两边加权平均价计算 `pairCost`；
- 用 `projectedPairCostIfBuy` 计算补仓后的成本；
- 失衡时优先买较少的一边；
- 有单边持仓超时、硬成本上限、单场亏损和尾盘停止；
- 支持手续费感知的吃单补仓判断；
- 可根据 BTC 波动缩小目标失衡和下单份数。

当前不足：

- `stableLive()` 仍以固定 `clipShares=25` 为主；
- 没有把盘口消费速度和真实排队概率纳入下单数量；
- maker 返佣和流动性奖励没有作为已确认收入计入回测；
- `fairValueGate` 在锁定生产配置中关闭，不能把 BTC 方向预测当作已验证优势。

## 推荐的动态补仓公式

设当前较重一边为 A，准备补较轻一边 B：

```text
qA, CA = A 的数量和累计成本
qB, CB = B 的数量和累计成本
aA = CA / qA                         (A 平均成本)
pB = B 的预计成交全成本              (价格 + 手续费 + 滑点缓冲)
T  = 本次目标配对成本
H  = T - aA                           (B 允许达到的平均成本)
```

补 `x` 份后的配对成本为：

```text
pair_after(x) = aA + (CB + x*pB) / (qB + x)
```

若当前 B 平均价高于 `H`，且 `pB < H`，把 B 平均价拉到目标附近所需的最低数量为：

```text
x_min = (CB - H*qB) / (H - pB)
```

实际下单数量不能只取 `x_min`，还要同时满足：

```text
x <= 可用资金
x <= 单边库存上限
x <= 失衡上限
x <= 盘口可见数量 × 保守成交系数
x <= 尾盘剩余时间允许的数量
```

如果 `pB >= H`，继续补仓不能把平均成本拉到目标值，应停止追价或改为等待更好的价格。

## 每次决策的正确顺序

1. **先算硬风险**：补完后最坏结算、手续费、滑点、未配对数量是否超限。
2. **再算可恢复性**：另一边当前盘口是否有足够数量，最高可接受价格是多少。
3. **再算成交概率**：盘口同价位排队量、最近成交消耗速度、挂单寿命和行情波动。
4. **再选价格和数量**：在安全范围内选择预期净收益最高的档位。
5. **挂单期间复检**：价格、盘口、BTC 波动或成交概率恶化就撤单重算。
6. **单边超时处理**：只在手续费计入后仍满足硬上限时才吃单；否则停止扩大风险。
7. **尾盘收口**：只允许降低失衡，不再开新的净敞口。

## 预期净收益评分

奖励不能当作确定收入。只有真实账户流水确认后才加入；回测默认按 0。

```text
score(action) =
    P(pair_complete) * locked_edge
  - P(unhedged) * worst_unhedged_loss
  - P(adverse_selection) * markout_loss
  - gas_and_operational_cost
  + verified_rebate
  + verified_reward
```

其中：

- `locked_edge = 1 - pair_after - 已确认费用`；
- `P(pair_complete)` 来自队列和成交流量模型，不是“碰到价格就一定成交”；
- `worst_unhedged_loss` 必须按另一边最终不成交计算；
- `verified_rebate/reward` 没有逐笔证据时固定为 0。

## 最终建议

最好的可落地方案不是让大模型实时决定下单，而是：

```text
实时盘口/成交/BTC → 硬风控数学模型 → 成交概率模型 → 候选价格和数量评分 → 撤单/重挂状态机
```

大模型只适合做离线分析和参数研究，不放在毫秒级下单热路径。

下一阶段应优先实现：

1. 动态 `x_min/x_max` 补仓数量；
2. 补腿最高可接受价格和安全余量；
3. 基于盘口流量的成交概率；
4. 自适应挂单期限和重挂阈值；
5. 每个候选动作记录“为什么下单/为什么拒绝”；
6. 回测中手续费、滑点按保守值计入，返佣奖励默认 0。

必须明确：成交概率是公开数据下的保守估算，不是交易所承诺的真实排队位置。真实 maker/taker、手续费、返佣、奖励和本人订单成交优先级，仍留到最后通过已注册账户的小额验证校准。
