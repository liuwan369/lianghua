# 项目范围与完成状态

项目目标是使用真实公开行情，构建可审计的 Polymarket BTC 5 分钟双边交易系统：从行情、决策、订单、成交、结算到真实费用和钱包资金均可追踪。系统采用都柏林服务器和原设计六页控制台，不以减少页面或隐藏未实现功能作为交付。

## 实现范围

| 层级 | 已实现 | 交付缺口 |
|---|---|---|
| 行情证据 | 都柏林采集、原始证据、公开市场发现、每 token tick 校验 | 市场切换新鲜度及负载稳定性持续验收 |
| 策略 | maker 配对、动态缺边修复、预算和库存约束、含费成本、拒绝日志 | 对冲完成率与残余风险政策未实盘验证 |
| 执行 | paper、V2 CLOB 适配、部分成交/撤单负债、在途控制、退出核对 | 真钱订单全生命周期与故障恢复端到端 |
| 账户 | 检查/保存，实际 V2 授权范围，已有 API key 私有查询 | 资产与真实账单完整展示、启动联动 |
| 六页前端 | 原设计、行情/状态/账本、六项参数保存、账户操作 | 交易控制、其他高级设置、筛选导出、到账证据与遥测 |
| 运行平台 | HTTPS 公网入口、都柏林 systemd 服务、后台读模型 | 高 CPU steal、SDK 冷启动与长期负载待验收；重复盘口计算和空闲账本已优化 |

## 完成标准

1. 保持六页设计，把每个可操作控件对应到明确后端能力；未知值、失败、未保存与未接入状态可区分。
2. 账户、余额、持仓、市场最小数量、tick 和配置在启动前联合校验，真实控制具备授权边界。
3. 在真实市场验证小额下单、部分成交、撤单、替换、网络恢复、迟到回报与退出收敛，保留交易所证据。
4. 逐笔核对成本、真实手续费、结算、返佣和奖励到账；账本和钱包资金可解释地对齐。
5. 在预期负载下验证 CPU、行情新鲜度、账户响应及遥测，不因资源优化丢失行情或改变策略语义。
6. 将未配对库存、最小份数残余及高成本缺边的处理政策明确并验证，不能把候选阈值当成保证平仓。

当前判定为 **NOT_READY_FOR_LIVE_TRADING**。代码存在、接口成功、账户预检和单元测试是分层证据，任何一项均不能单独代表系统全面验收或盈利。
